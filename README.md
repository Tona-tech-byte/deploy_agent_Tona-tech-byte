# Automated Project Bootstrapping & Process Management

## Overview

This project uses a Bash script to automate the deployment and management of a Student Attendance Tracker. The script creates the required directories, copies application templates, prepares a student roster, configures attendance thresholds, checks file permissions, runs the application, and archives log files.

It also handles deployment interruptions by creating a ZIP archive of the incomplete project and removing its incomplete directory.

## Requirements

Before running the script, make sure the following are available:

- Bash
- Python 3
- `zip`
- `sed`, `cp`, `mkdir`, `chmod`, and other standard Linux utilities
- ShellCheck for optional script validation

The script checks that Python 3, `zip`, and the required template files are available before deployment.

## How to Run the Script

Open a terminal in the repository directory and run:

```bash
chmod +x deploy_agent.sh
./deploy_agent.sh
```

The script displays a menu with four options:

1. Deploy application
2. Run application
3. Archive logs
4. Exit

Enter the corresponding number and follow the prompts.

## Feature 1: Deploy Application

Select option **1** to deploy the Student Attendance Tracker.

### Deployment process

The script:

1. Checks that Python 3 and `zip` are available.
2. Verifies that all three required template files exist.
3. Requests a project name suffix.
4. Creates the project directory and required subdirectories.
5. Copies the application and configuration files from the templates.
6. Allows the user to create a roster using either existing template students or a fresh roster.
7. Offers the option to update attendance warning and failure thresholds.
8. Verifies the required file permissions.
9. Runs the application to verify the deployment.

For example, entering `demo` creates a project named `attendance_tracker_demo`.

If that project already exists, the script asks whether it should be overwritten. Choosing `n` cancels deployment without changing the existing project.

### Deployed application structure

A successfully deployed project contains the following structure:

```text
attendance_tracker_demo/
├── attendance_checker.py
├── Helpers/
│   ├── assets.csv
│   └── config.json
├── reports/
└── archives/
    ├── attendance/
    └── absent/
```

The `reports/` directory stores the attendance and absence logs generated by the application. The `archives/` directories store timestamped copies of those logs.

### Roster configuration

During deployment, the user chooses between two roster options.

**Option 1: Copy students from the template**

The script asks how many students to copy from `templates/assets.csv`. It preserves the CSV header and copies the requested number of student records. This option assumes the template students have four previous sessions and sets `total_sessions` to `5`.

**Option 2: Generate a fresh roster**

The script asks how many students to include, allowing between 1 and 10 students. It generates the roster from predefined sample names and email addresses, with attendance and absence counts initially set to zero. It sets `total_sessions` to `1`.

These options allow the user to deploy the application with either existing student records or a new sample roster.

### Attendance thresholds

The script asks whether the user wants to update the attendance alert thresholds.

The default values are:

- Warning threshold: `75`
- Failure threshold: `50`

If the user chooses to update them, the script accepts whole numbers from `0` to `100` and modifies the corresponding values in `Helpers/config.json`. If the user keeps the defaults, the existing template values remain unchanged.

### File permissions

The deployment script applies the following permissions:

```bash
chmod +x attendance_checker.py
chmod 600 Helpers/config.json
```

The Python application is made executable, while the configuration file is restricted to read and write access for its owner.

The script then verifies these permissions before starting the application.

## Feature 2: Run an Existing Application

Select option **2** to run an already deployed attendance tracker.

Enter the project suffix when prompted. For example, entering `demo` selects `attendance_tracker_demo`.

The script checks that the project directory and required application files exist, changes into the project directory, and runs:

```bash
python3 attendance_checker.py
```

The application records attendance and creates the relevant log files in the `reports/` directory.

## Feature 3: Archive Logs

Select option **3** to archive the logs of an existing project.

Enter the project's suffix when prompted. The script checks for the following files:

- `reports/attendance.log`
- `reports/absent.log`

If a log exists, the script copies it into its corresponding archive directory using a timestamp in the filename.

Example:

```text
attendance_tracker_demo/
├── reports/
│   ├── attendance.log
│   └── absent.log
└── archives/
    ├── attendance/
    │   └── attendance_20261014_120000.log
    └── absent/
        └── absent_20261014_120000.log
```

The timestamp in this example is illustrative. The actual filename uses the date and time when the archive operation runs.

If a log is missing, the script displays a message instead of treating the missing file as an automatic failure. If neither log exists, it reports that no log files were available for archiving.

## Deployment Interruption Handling

The script installs signal handlers for `SIGINT` and `SIGTSTP` during deployment.

If deployment is interrupted while the deployment flag is active, the script:

1. Displays an interruption message.
2. Creates a ZIP archive of the incomplete project directory.
3. Names the archive `attendance_tracker_<suffix>_archive.zip`.
4. Removes the incomplete project directory.
5. Exits with a non-zero status.

For example, interrupting the deployment of a project with suffix `demo` produces:

```text
attendance_tracker_demo_archive.zip
```

The ZIP file preserves the incomplete project directory as it existed when the interruption was handled. Its contents depend on how far deployment had progressed.

Once deployment setup has finished, the script sets the deployment flag to false and starts the Python application. At that stage, pressing Ctrl+C stops the application rather than invoking the incomplete-deployment cleanup handler.

## Testing and Verification

The following checks can be used to verify the deployment agent.

### 1. Validate the Bash script

Run:

```bash
shellcheck deploy_agent.sh
```

A successful ShellCheck run produces no warnings or errors.

### 2. Verify the deployed structure

After deploying a project with the suffix `demo`, run:

```bash
find attendance_tracker_demo -maxdepth 3 -print
```

This displays the project directories and files, including the application, configuration, roster, reports, and archive directories.

### 3. Verify file permissions

Run:

```bash
ls -l attendance_tracker_demo/attendance_checker.py
stat -c '%a' attendance_tracker_demo/Helpers/config.json
```

Confirm that `attendance_checker.py` is executable and that the configuration file reports permission `600`.

### 4. Test application execution

Run the application through menu option 2. Confirm that it starts and processes attendance records. After a run that records attendance, check the generated logs:

```bash
ls -l attendance_tracker_demo/reports/
```

### 5. Test log archiving

Use menu option 3 to archive the logs. Then check the archive directories:

```bash
find attendance_tracker_demo/archives -type f -print
```

Confirm that existing logs are copied into the appropriate directories with timestamped filenames.

### 6. Test interruption handling

Start a new deployment and interrupt it with Ctrl+C or Ctrl+Z while deployment is in progress.

Verify that the script attempts to create the corresponding `_archive.zip` file and remove the incomplete project directory.

Check the ZIP archive's contents with:

```bash
unzip -l attendance_tracker_demo_archive.zip
```

Replace the example suffix with the suffix used during the test. The archive should contain the project files and directories created before the interruption.

## Conclusion

The deployment agent automates the setup and management of the Student Attendance Tracker through a single Bash script. It reduces manual setup, supports different roster configurations, validates file permissions, provides log archiving, and includes cleanup and backup handling for interrupted deployments.
